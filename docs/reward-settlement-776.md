## Proposed adapter contract (no implementation or approval implied)

1. Server builds immutable generation/season/day input from approved snapshot, current world CAS, exact source hashes, rule version and authorized funding/hold identity. Day28: confirmed domestic and cup entrants (16/24, unique canonical keys, matching exact approved season membership). Day56: verify full sporting chain, rank full regular/league phase and derive each unique cup outcome from verified progression (1/1/2/4/4/12). Validate complete coverage, IDs, no duplicate or unknown result, points/rank and outcome cardinality; never infer entitlement from displayed data.
2. Pure allocation calls shared competitionRewards, placementReference, participationReference, pointsReference and plannedRewardInstallments. Output deterministic component rows (competition, club, component, installment, amount, source evidence/version). Cross-check each component, competition, payday and world sum; zero amounts are recorded in the plan but never posted as zero journal entries. Unknown rule version, source mismatch, incomplete or zero denominator, unresolved tie, odd unsupported installment => blocked. No speculative fallback. Use stable canonical sort (not locale/display names) for serialization, not implicit remainder priority. Rule selection must be pinned to season and not silently use latest draft.
3. Before writes, proposed manifest digest over canonical version/evidence/rows; ledger policy version binding is explicit (do not assume draft-5 equals active finance policy). Reuse existing event receipt and hold/ledger evidence where sufficient; prove durable immutable plan reconstruction or request approval for smallest missing persistence. No new balance/ledger table. Annual budget hold of 2.4M ARC only after separately authorized reserve funding/activation; no grant or mint on payday. Day28 consumes 676800; Day56 consumes 1723200; full-world preflight ensures funds/treasury IDs and validates all 18 competitions. Ledger posting per positive component/club/installment, bounded batches/resume; no promise of world-wide atomicity.
4. Proposed stable business key reward:<generation>:<season>:<competition>:<component>:<club>:<day>; same semantic key independent of amount/version/hash so changed inputs cannot double pay. Derive stable request key within 160 chars (hash if needed), immutable source digest, stable authorized service actor (not changing admin caller on retry); guards bind live authorization, exact world/CAS/source/event/hold/version. Different amount/actor/source under same business key => conflict, not a second payout. Reversal is a separately approved compensating entry, never delete or silently overwrite.
5. Compare expected rows to exact journal receipts (purpose, actor, source, key, amount, version, generation, day, accounts, hold), reject unexpected/missing/mismatched or reversed receipts; reconcile totals, hold remaining, reserve/treasury deltas and global ledger. Read failures/timeout => unknown, retry same keys; partial batch => pending, resume missing only, no payroll or next day until complete. A genuine mismatch freezes through #775 authorized workflow, not a new ledger. No automatic correction or duplicate issuance. Event completed only after reconciliation with guarded manifest/receipt digest; ensure concurrent writer/reset/version changes cannot invalidate check. Production-scale D1 query/batch/guard limits and bounded reconciliation are open release gates.
